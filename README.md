# Horizon | End-of-Life Tracker

Horizon tracks a program to retire two end-of-life Linux versions, **Ubuntu 16.04** and
**Oracle Linux 7**, across an enterprise server fleet. It compares what host owners
**planned** to decommission each month with what **actually** left the inventory, at the
OS, portfolio and owner level, and shows who is on track, who is behind, and who has no
plan at all.

This repository is a portfolio rebuild of a dashboard I originally built to run that
kind of program. The original ran against a live inventory system. This version runs on
a **synthetic, point-in-time dataset** so it can be shared publicly.

> **All data is synthetic.** Hosts, owners, host counts and plans are generated by a
> seeded script. Names are invented and hostnames and IP addresses use reserved example
> ranges. Nothing here describes a real company's infrastructure.

## Quick start

Requirements: **Python 3.9+** and **Node.js 18+**.

```bash
git clone https://github.com/LavMural/horizon-eol-tracker.git
cd horizon-eol-tracker
./run.sh
```

Then open **http://localhost:8000**. The first run installs packages, which takes a
minute or two. Press `Ctrl+C` to stop.

`run.sh` creates a Python virtual environment, installs the backend, builds the
frontend, and serves the whole app (page, API and API docs at `/docs`) on one port. On
first launch the demo database is generated automatically.

## What's in the app

### Insights

- **OS summary cards.** For each OS: remaining hosts vs the baseline, % complete, net
  change since the last refresh, run rate, projected completion date and data-quality
  flags. A status tag shows whether the projection lands inside the program window. In
  the demo, Oracle 7 is on track and Ubuntu 16.04 is at risk.
- **On track / Behind / No plan badges.** Every remaining host is counted in exactly one
  bucket, decided **per owner**, so the three numbers always add up to the remaining
  total. Hover a badge to see its portfolios, and click a portfolio to see its owners.
  An owner is judged only against decommissions due by the end of the **last completed
  month**, so nobody is marked behind for a month that is still in progress.
- **Filters.** Pick an OS and any set of portfolios. The selection persists across tabs
  and reloads.
- **Burndown.** Planned vs actual remaining hosts by month, with the actual line
  stopping at the current month.
- **Planned v Actual.** Decommissions per month. Click an **Actual** bar to list the
  hosts that left that month and whether each was decommissioned or upgraded.

### Planned

- An editable monthly grid of plan lines (OS, portfolio, application, owner, hosts per
  month), with unsaved-change tracking, row and month totals, duplicate and delete.
- Portfolio is chosen from known portfolios and owner is autocompleted from the
  inventory, so plans join to actual hosts exactly. Unknown values are flagged.
- A stacked bar chart of planned decommissions, grouped by portfolio, owner or
  application.
- Bulk import from CSV or Excel (with a downloadable template). Imports update matching
  lines in place and report unknown portfolios and owners.
- An **activity log** of every create, update, delete and import, with before and after
  values, who made the change, and CSV export. Each row shows who changed it last.

### Actuals

- Data-quality counts per OS: hosts with an unknown portfolio, no owner, a departed
  owner, or remediated since the last refresh.
- **Owner triage**: new owners, owners with no portfolio, departed owners and unowned
  hosts. Assigning a portfolio updates the mapping and re-files that owner's hosts
  immediately.
- Remaining hosts by portfolio, a "needs review" host list with CSV export, and the daily
  refresh history.

### Mapping / Settings

- Portfolios with short and full names, and whether each comes from the owner mapping
  or only from the inventory feed.
- The owner-to-portfolio map and owner status, both editable.
- Program settings (tracked OS, reporting window, baseline and as-of dates) and a
  **Reset demo data** button that restores the original dataset.

## How the numbers work

- **Baseline.** The hosts on each EOL OS on **June 15, 2026**. Progress is measured
  against this fixed population.
- **Planned.** Host owners give the number of hosts they will take off the EOL OS in each
  month. Planned remaining = baseline minus cumulative planned decommissions.
- **Actual.** A host counts as done when it is decommissioned or upgraded to a supported
  OS.
- **Portfolio.** Taken from the inventory feed when present, otherwise from the owner
  mapping, otherwise "Unknown". Unknown hosts are never dropped; they surface in triage.
- **"Today".** The dataset represents **September 15, 2026**. The app never reads the
  real clock for its calculations, so the dashboard looks the same whenever it is
  opened.

The test suite checks that these numbers reconcile: the badges add up to the headline
count, and selecting every portfolio gives the same totals as "All portfolios".


## Development

Run the backend and frontend separately to get hot reload while editing:

```bash
# terminal 1: API on :8000
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000

# terminal 2: frontend on :5173 (proxies /api to :8000)
cd frontend
npm install
npm run dev
```

Other useful commands:

```bash
cd backend && .venv/bin/python -m pytest -q                  # run the tests
cd backend && .venv/bin/python scripts/generate_mock_data.py # rebuild the demo database
```
